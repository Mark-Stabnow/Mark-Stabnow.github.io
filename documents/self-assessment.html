CS 499 · Final ePortfolio

Professional self assessment

The capstone pulled several parts of the computer science program into one project. I had to look at the same application as a user interface, an API, a set of algorithms, a database, and a security problem. That was more useful to me than treating each topic as an isolated assignment because a change in one layer could affect the others.

Communication became part of the technical work. The code review had to explain the original Android project to a peer or manager. The enhancement narratives had to explain what changed, why I chose it, and what the evidence actually showed. I also had to keep the limits visible. A loaded view search in the browser is not the same thing as a warehouse wide search, and a local benchmark does not prove production performance.

The software engineering work made separation of responsibilities more concrete. The original Android screen classes handled form checks, database work, filtering, and drawing the interface. In the PWA, the browser handles the interface and local state, the Express API handles sessions and validated requests, and repository code handles PostgreSQL access and transactions. The offline stock queue also forced me to think about failure instead of only the normal path. A stable request ID is needed because the server can accept a change even when the browser never receives the response.

The algorithms work reinforced that a more complicated structure is not automatically better. I implemented a hash map for exact SKU lookup, a trie for prefix matching, and a min heap for lowest stock selection. On the recorded 1,000 item benchmark, exact SKU lookup and lowest stock selection were faster after the indexes were built, while prefix search was slower than the normalized array scan. The update medians were close enough that I would not claim a meaningful advantage from that measurement alone.

The database work made preservation and verification just as important as schema design. The Android export excludes account credentials, the importer validates records before writing, and the migration keeps source IDs and timestamp text so imported records can be traced back to the original data. The reconciliation view reports quantity disagreements instead of silently changing them. I also learned to separate completed checks from checks that still need the right environment.

The finished portfolio gives me something I can walk through from the original source to the enhanced code and the evidence that supports it. I can explain what I changed, where the design still has limits, and why I made those tradeoffs without turning the project into something bigger than it is.

This assessment is based on the CS 499 code review, enhancement narratives, implementation notes, and verification evidence in this repository.
