Professional self assessment

What I learned from the capstone

The capstone pulled several parts of the computer science program into one project. I had to look at the same application as a user interface, an API, a set of algorithms, a database, and a security problem. That was more useful to me than treating each topic as an isolated assignment because a change in one layer could affect the others.

Communication became part of the technical work. The code review had to explain the original Android project to a peer or manager. The enhancement narratives had to explain what changed, why I chose it, and what the evidence actually showed. I also had to keep the limits visible. For example, a loaded view search in the browser is not the same thing as a warehouse wide search, and a local benchmark does not prove production performance.

The software engineering work made separation of responsibilities more concrete. The original Android screen classes handled form checks, database work, filtering, and drawing the interface. In the PWA, the browser handles the interface and local state, the Express API handles sessions and validated requests, and repository code handles PostgreSQL access and transactions. The offline stock queue also forced me to think about failure instead of only the normal path. A stable request ID is needed because the server can accept a change even when the browser never receives the response.

The algorithms work reinforced that a more complicated structure is not automatically better. I implemented a hash map for exact SKU lookup, a trie for prefix matching, and a min heap for lowest stock selection. On the recorded 1,000 item benchmark, exact SKU lookup and lowest stock selection were faster after the indexes were built, while prefix search was slower than the normalized array scan. That result is more useful than claiming every custom structure improved performance.

The database work made preservation and verification just as important as schema design. The Android export excludes account credentials, the importer validates records before writing, and the migration keeps source IDs and timestamp text so imported records can be traced back to the original data. The reconciliation view reports quantity disagreements instead of silently changing them. I also learned to separate completed checks from checks that still need the right environment.

The finished portfolio gives me something I can walk through from the original source to the enhanced code and the evidence that supports it. I can explain what I changed, where the design still has limits, and why I made those tradeoffs without turning the project into something bigger than it is.

Primary artifact

Warehouse Inventory App

The original artifact was created in CS 360 as an Android application. It included account login, inventory cards, search, quantity changes, restocking, and text alert settings. Data was stored locally with SQLite.

For CS 499 I rebuilt the inventory workflow as a progressive web app. The browser client uses React and TypeScript. An Express API handles sessions, validation, permissions, and write requests. PostgreSQL stores inventory, stock history, audit records, and migration state. The project also includes an offline stock queue, loaded view indexes, import tooling, and automated checks.

The goal was not a feature for feature copy. I kept the warehouse workflow and changed the design where the original structure made testing, disconnected use, or data history difficult.

Three enhancement areas

What changed and what I learned

01

Software design and engineering

Move responsibilities out of the screen code

The original Android project put form checks, database calls, filtering, and UI work in the same screen classes. I rebuilt the workflow as a React and TypeScript client talking to an Express API. Client modules handle API calls, cached inventory, and queued stock changes. Server routes check the session and permission before validated requests reach repository and transaction code.

The hardest part was the stock count when a connection drops. A browser can show a local action before the server accepts it, and the server can accept a request even if the response never makes it back. I used a stable request ID so retries cannot apply the same stock change twice. Pending changes stay separate from the confirmed count.

Security changes include salted scrypt password hashing, timed account lockout, login request limits, session cookies, cross site write checks, and API level role checks. Managers can manage items and stock, clerks can record stock changes, and viewers remain read only.

Course outcome evidence: software architecture, testing, communication, and security. These protections are specific to this course project and are not a claim that the application is ready for a real warehouse.

02

Algorithms and data structures

Add local indexes without pretending they search the whole warehouse

I implemented a separate chaining hash map for exact SKU lookup, a trie for prefix matching, and a min heap for lowest stock selection. An InventoryIndex coordinates the structures and rejects duplicate SKU updates without damaging the existing index state. The browser builds those indexes only over records that have already been loaded.

I kept warehouse wide search on the API. The local controls are labeled as loaded view tools, and a local miss does not claim that the SKU is missing from the warehouse. That distinction became part of the algorithm design, not just a UI label.

03

Databases

Preserve the original data and make stock history checkable

The original Android database overwrote quantities and its upgrade path dropped existing tables. For the database enhancement I added a Python exporter that reads the Android inventory table without exporting usernames or password hashes. A Node importer validates the exported data, reports missing fields, invalid quantities, and duplicate SKUs, and previews the changes before writing.

The import keeps the original item IDs linked to the new records and preserves the Android timestamp text instead of inventing a timezone. Category and reorder level are supplied during import because those fields did not exist in the original database. Each accepted item gets an opening stock record because the Android app did not have earlier stock history to recover.

A second SQL migration adds import provenance, constraints, indexes, and a reconciliation view without rewriting the first migration. The reconciliation check compares the stored quantity with the total from stock history and reports disagreements instead of silently changing data.

Verification status

The Milestone Four preparation record reports 99 named dependency free automated tests passed with 0 failed and 0 skipped. It also records a real SQLite to JSON to Node mapping pipeline for exactly 1,000 items, along with source preservation and syntax checks.

The same record is explicit about what was not run in that environment: the full TypeScript build, PostgreSQL integration suites, migration and restore checks, SQL query timing, and the 13 Chromium browser workflow tests. I am keeping that distinction visible instead of treating planned checks as completed evidence.

Course outcome evidence: migration design, transactions, constraints, import validation, source preservation, and privacy of account data.
